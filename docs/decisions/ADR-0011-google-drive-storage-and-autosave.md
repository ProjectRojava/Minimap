# ADR-0011: Google Drive as the shared store, with autosave, multi-device merge and media

Supersedes ADR-0002.

- **Context**: ADR-0002 allowed network access and added Google Drive as an off-device *backup* destination. The owner's direction (spec 22): Google Drive is Minimap's data store and media store, data autosaves to it continuously, and the app must **sync seamlessly across several computers**. CLAUDE.md requires local-first operation and a single user (§1), all structured data in one SQLite file (§1), and a live database that never sits in a synced folder (§8, spec 20). SQLite cannot safely run on a network drive or inside a sync folder, and Drive has no transactions, so two devices cannot share one database file.
- **Decision**:
  1. **Network access** (carried over from ADR-0002): allowed for features the user connects. No telemetry or analytics. User data leaves the device only to a destination the user has connected. All HTTP runs in the Rust backend (a new crate, `minimap-sync`); the webview CSP stays closed to the network.
  2. **Every device keeps a full local working copy; Drive carries each device's snapshot.** The app reads and writes `<app_data_dir>/minimap.db` as before (fast, transactional, offline). Once Drive is connected, an encrypted snapshot of it is autosaved to `Minimap/devices/<device_id>.db.enc`. Each device writes **only its own file**, so devices can never overwrite each other and no lease, lock or "take over" exists. Drive stays optional; without it the app works as before and the user is warned persistently that data is on this device only (status bar chip, a This week banner dismissible for 7 days, Settings, first-run notice).
  3. **Seamless sync = automatic state merge.** Every 15 s a device lists the other devices' files and merges any that changed into its own database in one transaction, then saves its own snapshot if the merge changed anything (so the others receive the combined state). Merge rules:
     - Rows match by `id` (edges by `(edge_type, from_id, to_id)`); the later `updated_at` wins the whole row; ties break on a stable content hash, making the merge deterministic and symmetric (A into B = B into A) and idempotent, which gives convergence without coordination.
     - Hard deletes leave **tombstones**, which beat edits.
     - Activity is unioned by id. Work-related settings merge per key by `updated_at`; per-device settings never sync.
     - Rules the database cannot express are re-checked after merging and **repaired, with each repair reported**: duplicate project handles (later-created renamed), two self people (incoming demoted), loops in `blocks` / `depends_on` / `supersedes` / `reports_to` / team nesting (newest link in the loop archived), dangling links and pointers (removed / cleared).
  4. **Known limit, accepted**: rows merge whole, so two devices editing different fields of the same item between syncs lose the earlier save's fields (history keeps both). Field-level merge and three-way text merge of notes are out of scope. "Newest" uses device clocks; Settings warns of a clock more than 2 minutes off Google's.
  5. **Autosave timing**: after a committed write, upload once the app has been idle for 5 s, and no later than 30 s after the first unsaved change; also on close (flush up to 10 s, else queue), reconnect and wake. The snapshot is the SQLite online backup into a temp file keyed with the vault key before any page is written; device-local rows are removed from it before upload. The DB lock is held only for the copy and for the merge transaction.
  6. **Atomic, retried saves**: a device's snapshot is replaced only by a completed upload; failures keep the previous one and retry with backoff (5 s, 30 s, 2 min, then every 10 min). Hourly and daily **checkpoints** (default 24 + 30) are kept; retention deletes only app-named files. A checkpoint can be **recovered** (changed or deleted items come back as new edits; newer items stay), because a whole-database rollback would be undone by the next sync from the other devices.
  7. **Media (attachments) on Drive**: encrypted, content-addressed blobs `Minimap/media/<sha256>.bin` (deduplicated), metadata in an `attachments` table that merges like any row. A local cache in `<app_data_dir>/media/` (encrypted blobs, LRU, default 2 GB) never drops a blob not yet on Drive; per-file limit 250 MB. Allowed kinds: images (incl. SVG), Markdown/text/CSV, PDF, Word, Excel, PowerPoint and equivalents; executables and scripts are refused.
  8. **Encryption of everything uploaded**, independent of whether the local DB is encrypted (spec 21): a random 256-bit **vault key**, created when first needed, stored in the local database (`app_meta`, encrypted when DB encryption is on, never uploaded, kept across restores) and shown once as a recovery key at first connect. Snapshots and checkpoints are SQLCipher databases keyed with it; media blobs use XChaCha20-Poly1305 in a chunked streaming construction. `Minimap/vault.json` holds a format version and an encrypted key check so a wrong recovery key is refused before anything changes. Keys, tokens, file names and note content are never logged.
  9. **OAuth**: desktop flow with loopback redirect + PKCE, `drive.file` scope only (the app sees only files it created, on any device using the same OAuth client). The refresh token goes in the OS keychain, or in the local database where there is no keychain. The client ID and secret are supplied by the build (`MINIMAP_GOOGLE_CLIENT_ID` / `_SECRET`) or by the user in Settings.
  10. **Rendering media**: attachment images are served by the backend through a custom Tauri URI scheme (`minimap-media`), never a network URL, and SVG only ever as an image. This amends spec 09's rule "images show their alt text only": attachments render; external images are still never fetched.
  11. **Local backups stay** (spec 20): the daily local backup keeps running so a Drive outage or account problem never leaves the user without a copy. A `pre-sync` backup is taken before a device's first merge and before any merge that removes more than 20 rows.
- **Consequences**:
  - CLAUDE.md §1 reads: structured data in one SQLite file; attachments are blobs stored alongside (Drive plus local cache). §8 describes Drive storage, autosave and multi-device merge instead of Drive backup.
  - New crate `minimap-sync` (depends on types and store; owns crypto, the Drive client, OAuth and the sync engine; no SQL). New dependencies: `reqwest` (rustls), `chacha20poly1305`, `sha2`, `base64`. The store gains migration 0008 (`edges.updated_at`, `settings.updated_at` kept by triggers; `tombstones`; `attachments`) and the merge, snapshot and attachment repositories.
  - Every hard delete writes a tombstone; every edge or setting write must keep `updated_at` current (triggers do it, so new write paths are covered).
  - New permissions: the custom media URI scheme; the existing dialog-open permission is used for the file picker; opening an attachment is done by the backend.
  - Losing the recovery key makes Drive data unreadable on a new device (by design); existing devices keep their local copy and can start a fresh Drive.
  - Drive storage use grows with media; Settings shows Minimap's usage.
  - A Google Cloud project, OAuth client (Desktop type) with the Drive API enabled, and consent-screen verification for public distribution are required. The engine is tested against a folder-backed remote; the Drive HTTP client could not be exercised against Google in development and needs a manual check.
- **Alternatives rejected**:
  - **One shared snapshot with a writer lease and read-only second device** (the first draft): not seamless; Drive v3 has no conditional writes, so a lease is advisory only.
  - **SQLite file inside a Google Drive for Desktop folder**: the sync client can upload a half-written database or WAL and produce conflicting copies; corruption risk.
  - **Drive as backup only** (ADR-0002): leaves the latest work on one machine and gives a new device nothing to start from.
  - **Operation log / row-level change feed**: fine-grained merge, but needs every write path to emit operations and a compaction scheme; the existing activity log folds and loses detail, so it can't serve. State merge with tombstones needs only `updated_at` and gets the same convergence for a single-user data set.
  - **Media inside the SQLite file**: makes every snapshot carry all media and bloats the database.
  - **Reusing the DB key for Drive**: the DB key may be passphrase-only or absent, and a keychain key cannot move to a new device; a separate vault key with its own recovery key works in every mode.
  - **Relying on Drive's own file revisions** for history: limited in count and time and not under the app's control; explicit checkpoints are.

## Addendum: what was built (2026-10-05)
- **Tombstones carry `deleted_at` and `lifted_at`** (migration 0008) instead of "a tombstone beats any edit forever": a recovery from a checkpoint lifts the tombstone and must reach the other devices, and a later delete must beat that recovery. Both columns merge by taking the later value, and a tombstone counts only while it is newer than its lifting.
- **Change tracking** is `AppState::run_vault` comparing `total_changes()` around every command, not triggers or per-command calls; the engine's own writes are not tracked.
- **The UI polls** `get_sync_status` (every 4 s) rather than listening for events, so no event permission was added to the capability.
- **Tests**: the engine runs end to end with two simulated devices over a folder-backed remote; the Drive client, resumable upload and sign-in run against a mock Google server on localhost. A real Google account was not available; connect, upload and download against real Drive are a manual check.
- **Snapshot creation** uses `sqlcipher_export` (the backup API can't copy a plain database into an encrypted file), then removes device-local rows and compacts.
- An archived item keeps its attachments (hidden with it); the 2 GB cache limit and the 250 MB per-file limit are constants for now.
