# ADR-0017: Sub-tasks come back as a plain "part of" tree, apart from `blocks`

- **Context**: spec 31 relabelled the `blocks` link as *parent* and *child* (a parent waits for its children). That conflated two different relations. Sequencing ("B can't start until A is done") is a DAG that drives dates and may connect unrelated tasks, even across projects. Structure ("B is a piece of A") is a tree that groups work and rolls up progress. A task that blocks another without being part of it had no honest label, and choosing *Parent* to split a task silently added a scheduling constraint. ADR-0015 had removed sub-tasks because they were tangled up with the schedule (group scheduling, a blocks-on-a-group rule, graph frames), not because splitting a task is a bad idea.
- **Decision**: separate the two. `blocks` keeps its meaning and is worded *Blocks* / *Blocked by* everywhere (parent/child are no longer words for it). Sub-tasks return as the edge type `subtask_of` (sub-task → parent, task → task; the legacy value from ADR-0013 is reused, so no enum change and no migration: migration 0012 already archived the old rows). It is organisation only: **no effect on dates, the schedule, critical path, impact analysis, capacity, health or the dependency graph** (they read `blocks` alone).
- **Rules** (`core::subtasks::check_new`, enforced by `store::tasks::check_subtask` in `check_new_edge` and in `create_linked`): a task is part of **one** task, and the tree is **one level deep** (a parent is not a sub-task, a sub-task has no sub-tasks). One level means no cycle check is needed. The refusal names the tasks. A task may be a sub-task of one task and be blocked by or block any task, including its own parent.
- **Read model**: `TaskRow` gains `parent`, `subtask_count` and `subtasks_done` (cancelled and archived sub-tasks are not counted), so the board shows progress without more calls. The pane gets a *Part of* section apart from *Links*; the link dialog offers five relations in two rows (*Blocks this*, *Blocked by this*, *Related* / *Parent*, *Sub-task*); `LinkRelation` gains `Parent` and `Subtask`.
- **Consequences**: no new command, table or migration; undo, export, merge and sync handle the edge generically. Archiving a parent archives its links, so sub-tasks become ordinary tasks. A sync of an old, unmigrated snapshot may bring back old `subtask_of` rows; they now show as sub-tasks and a task could then have two parents on that device: the pane lists every parent with ✕, and the board shows the first. We did not add a merge repair for this (rare, visible, and easy to fix by hand). A parent can be marked done with open sub-tasks (nothing is enforced); the chip shows how many are open. Not built: deeper nesting, a parent's dates or status derived from its sub-tasks, quick-add syntax, indented Markdown export.
- **Deviation**: `CLAUDE.md` §4 gains the `subtask_of` row (the matrix lost it in ADR-0015) and the one-parent, one-level invariant. ADR-0015 stays accurate about what was removed then; this ADR supersedes its "no subtasks" outcome only for a plain tree.
