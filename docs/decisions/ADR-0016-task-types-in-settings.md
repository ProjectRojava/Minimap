# ADR-0016: The task-type list lives in Settings

- **Context**: tasks get a user-editable type (spec 32). The list is small (a handful of entries, edited rarely) and every device needs the same one. A node-like table of types would need its own activity, undo, merge, export, tombstone, demo-removal and search handling for what is configuration.
- **Decision**: keep the list as one JSON value under the settings key `task_types` (`[{id, name, hue, archived}]`), like the health thresholds, and store on each task only the type's `id` in `tasks.task_type` (nullable text, no foreign key). Until it is edited the list is `default_task_types()`; a stored list that no longer validates falls back to it.
- **Why not names**: a rename must not orphan tasks, so the id is stable (made from the name once, unique, never changed). A type is never removed, only archived, so no id a task holds is ever dangling on one device.
- **Consequences**: settings already sync (per key, newest write wins) and are backed up, so types need no new sync code. Two devices editing the list at the same time lose the older edit (rare for configuration). A task that points at an id missing from the list (possible only through such a merge) simply shows no label. Changes to the list are not undoable and not in the activity log, like other settings; a task's own type change is (the `task_type` diff key, a `Patch` field in `undo::nullable_fields`). The list is exported as `task_types.json` because a task's `task_type` is meaningless without it.
- **Deviation**: `CLAUDE.md` §4 gains `task_type` on the task.
