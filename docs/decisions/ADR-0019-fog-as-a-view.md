# ADR-0019: Fog of war: staleness is a view, not a status

- **Context**: health (spec 15) says what the data says; nothing says how long ago anyone looked at it. A project can read *On track* because nobody has touched it in three weeks. We want work that is in play but untouched to look its age, everywhere it appears, with a quick way to say "still accurate" (spec 43, `docs/product-design/01-fog-of-war.md`).
- **Decision**:
  - **Fog is computed, never stored as a status.** `minimap_core::fog::build` turns dates into a `FogReport` (marks for hazy and fogged items, a visibility percent). It reads items, the dates of link changes (from the activity log) and the dates of notes that mention them; it writes nothing. It never changes health, schedule, capacity or impact.
  - **Only what is in play can be fogged** (an active project; an open task that is under way, blocked, due within 14 days or in focus; an objective that is not done and not ongoing). Closed, paused, far-off, meeting and ongoing-objective items never are. Ongoing objectives already have a review rhythm (spec 30).
  - **One new stored fact: `confirmed_on`** (a date, nullable) on tasks, projects and objectives: the day someone said "still accurate". Last seen is the newest of the item's `updated_at`, `confirmed_on`, its link activity, the notes that mention it and, for a project or objective, what vouches for it (its tasks in play, its contributors). Thresholds are a synced setting (`fog`).
  - **Confirming is not an edit.** `store::fog::confirm` is a logged update of `confirmed_on` only, and when `confirmed_on` is the only field that changed the repo **leaves `updated_at` alone** (`activity::only_confirmation`). Otherwise an undo (which is an update too) would stamp the item as freshly changed and could not bring the fog back, and "last changed" would stop meaning a change.
  - **One report, looked up by id.** `get_fog` returns the whole `FogReport`; the UI keeps it in a context (`FogCtx`) and looks marks up by id, so no list DTO changed. `get_this_week` also takes the report for its *Gone quiet* section (`WeekInput.fog`, `ThisWeek.quiet`): fogged tasks that are not already on the page, at most 8. Looking back at a past day (`as_of`) has no fog: the history of when things were touched is not kept in a form that can be rewound.
  - **The look is a fade and a chip, never colour alone** (`≋ 19d`, full contrast, with a hover that says why). Cards keep their type borders; fog does not change borders.
- **Why not a stored `health` reason or a status**: it would make an unattended item look "at risk" when it may be fine, mix two questions (is it going well / do we know), and need a write for what is only the passage of time.
- **Why not bump `updated_at` when confirming**: see above (undo). The cost is in sync: two devices that confirm the same item without any other change have the same `updated_at` and different content, so the merge takes the larger content hash (`core::sync::remote_wins`), which both devices pick alike; a confirmation can lose to an unconfirmed copy, which only means the fog shows again until it is confirmed once more. Any real edit carries its `updated_at` and wins as usual.
- **Consequences**: migration 0017 adds the column to three tables; the full export gets it for free (the structs are the files); undo needs `confirmed_on` in `nullable_fields` (done); the demo data backdates its history so the story reads (Platform Cost Reduction in fog, two Security tasks hazy, one task confirmed, EU Region clear). Old databases open with no confirmations. A new kind of node that should be fogged needs a rule in `core::fog`.
- **Deviation**: `CLAUDE.md` §4 gains `confirmed_on` on task, project and objective; §6 gains `get_fog` and `confirm_item`.
- **Related ADRs**: amends [ADR-0011](ADR-0011-google-drive-storage-and-autosave.md) (the one write that does not bump `updated_at`, and what that means for the merge), and extends [ADR-0014](ADR-0014-ongoing-objectives.md) (ongoing objectives are never fogged) and [ADR-0018](ADR-0018-meetings-as-a-built-in-task-type.md) (meetings are never fogged). ADR-0003's `Patch<T>` carries `confirmed_on` like any nullable field. Nothing else is changed.
- **Amended by [ADR-0020](ADR-0020-pings-as-a-light-table.md)** (pings): a ping on an item is not a sighting. It changes nothing on the item, `updated_at` included, so pinging an item does not clear its fog (*Still accurate* does).
