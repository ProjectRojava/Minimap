# ADR-0020: Pings: a light marker table, not a node type

- **Context**: an exec's version of a map ping is "come back to this on Friday": the vendor contract inside a project, a person to talk to, a decision to revisit. The closest tools are focus (tasks only, every day), waiting-ons (someone owes you something) and a task (too heavy: it enters the schedule, capacity and health). We want **a marker on any item with a day and an optional line of text** that shows on This week that day and changes nothing about the item (`docs/product-design/05-pings.md`).
- **Decision**:
  - **A small `pings` table** (migration 0018): `id`, `target_type`, `target_id`, `note`, `on_date`, `cleared_on`, `created_at`, `updated_at`, `archived_at`. It points at its target without a foreign key, like `edges` and `attachments`, because targets are polymorphic. It is **not a node type**: a ping has no page, no links of its own, no search entry and no detail pane.
  - **Why not a node type**: it would touch the search triggers, the edge matrix, `nodes::find`, the links editor, `NodeType::ALL` (merge, demo removal, edge rules) and every node switch in the app, for something with no screen of its own. **Why not an edge**: edges carry no dates, and archiving the target archives its edges, which would lose the ping.
  - **Rules in core** (`minimap_core::pings`): the note is trimmed, kept on one line and at most 200 characters; the day must be today or later (an unchanged past day is allowed, so a note can be edited after the day has passed); *live* = not archived and not cleared, and its target is active; *due* = live and `on_date <= today`; `arrange` splits live pings into due (oldest day first) and upcoming (soonest first). The store checks them in the same transaction.
  - **One live ping per item**, kept by the store inside the transaction: pinging an item that has a live ping changes that ping. There is **no unique index**, because two devices can each make one while offline; the merge repairs it (below).
  - **Clearing** sets `cleared_on` to the day (clearing again keeps the first day). A ping whose target is archived is hidden, not deleted; unarchiving the target brings it back. A hard delete of a target (`nodes::delete`) hard-deletes its pings and leaves tombstones.
  - **Activity and undo: the attachments precedent, not `NodeType::Ping`.** The spec allowed a `NodeType::Ping` variant used only by the activity log and undo, and said to use the attachments precedent if the variant leaked into every node match. It does (33 matches on `NodeType::WaitingOn` alone, plus the `ALL` loops), so every write logs an `updated` row **on the target** with a single `ping` key: `{"ping": [old, new]}`, where each side is the ping's state (`{id, note, on_date, cleared_on, archived}`, `null` before it existed). `minimap_core::undo` reads that key as **undoable** (`Inverse::Ping`): `store::pings::restore_in_tx` puts the ping back as it was (a new ping is removed), after checking it still is as the row says, and writes the rows redo is made from. A row that mixes `ping` with other keys, or has the wrong shape, is irreversible, like any unknown shape. The item's Activity list shows these rows, so the history of a ping is on the item.
  - **Sync** (ADR-0011): `pings` merges by id with the newest `updated_at` winning, hard deletes through tombstones of kind `ping`, and two repairs reported in the merge summary: pings whose target was deleted on another device are dropped, and **when both devices made a live ping on the same item, the newer is kept and the older is cleared** (on the day it was last written, so every device makes the same repair and nothing is stamped).
  - **Not searched**: a ping has no search entry; the note is private bookkeeping, never logged at info.
  - **Quick-add** gains the keyword `ping` and the keys `task:`, `objective:` and `decision:` (read as keys only on a `ping` line, so a title elsewhere can still say "decision: ..."). The quick-add directory now includes decisions. Pinging oneself (`@me`) is refused.
  - **Private bookkeeping**: pings are not in the weekly status report, not in health, not in the schedule, capacity or impact; `updated_at` of the target is untouched (so a ping does not clear fog).
- **Consequences**: the full export gets `pings.json` (`DataExport.pings`); `demo_remove` needs no new node type (a demo item's pings go with it through `nodes::delete`, and are counted); the demo data seeds three pings; the undo planner has one more row shape; `store::undo::ping_nullable_fields` mirrors `UpdatePing`'s `Patch` fields (a test keeps it honest). A new kind of thing that should carry pings needs nothing: any `NodeRef` works, and the quick-add grammar names the five kinds a line can reach.
- **Deviation**: `CLAUDE.md` §4 gains the pings table, §6 gains the ping commands (`list_pings`, `ping_item`, `update_ping`, `clear_ping`, `reopen_ping`, `archive_ping`, `get_ping_for`).
- **Related ADRs**: amends [ADR-0003](ADR-0003-activity-actions-and-patch.md) (a second kind of activity diff, `ping`), [ADR-0011](ADR-0011-google-drive-storage-and-autosave.md) (a table that merges by id with its own repair) and extends [ADR-0019](ADR-0019-fog-as-a-view.md) (a ping does not count as a sighting). Follows the attachments table of ADR-0011 for the shape of a polymorphic satellite table.
