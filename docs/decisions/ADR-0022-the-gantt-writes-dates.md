# ADR-0022: The Gantt writes dates, and pushes due dates, not start dates

- **Context**: the Gantt screen (spec 57) lets you drag a task's bar to change when it happens. The schedule is **derived**: a task's bar is where `schedule::compute` puts it (earliest start from its blockers, its own start date and today; length from its estimate), and a `due_date` is only a deadline that the schedule never reads. So "drag the right edge to Friday" has nothing to write unless we decide what it means. And moving one task later moves the tasks that follow it, whose dates the person never touched. Spec 14's *Apply to plan* (`impact::apply_plan`) already faced this and chose to **pin** the tasks the slip holds back (a start date) and leave the ones that are only pushed along by `blocks` alone, because pinning them would freeze work the schedule should keep moving.
- **Decision**:
  - **A drag writes dates and the estimate.** Middle: `start_date`, and `due_date` shifted by the same working days (the estimate is left). Left edge: `start_date` and `estimate_days` (the end stays). Right edge: `due_date` and `estimate_days` (the start stays; it is **not** pinned, so a task driven by its blockers stays driven by them). The estimate is written because it is the only thing that makes the bar end where it was dropped: it is the task's length in working days, which Minimap already treats as the task's size. Whole working days; a bar always keeps at least one.
  - **Followers are pushed in their due dates only.** `core::gantt::plan_drag` runs the schedule before and after on a copy of the plan; each other open task that finishes later gets its `due_date` pushed by `ceil(delta)` working days. **Never earlier** (a due date is a promise; this matches impact analysis's "a slip never moves a task earlier"), **never a start date** (so followers stay free, the point of spec 14's rule), **never a task without a due date**, and **never a project target** (that stays a choice, made by dragging the flag). This is a deliberate difference from *Apply to plan*, which pins the tasks it holds back and leaves the pushed-along ones with their dates; it goes one step further for due dates because here the person moved a bar they could see and asked for the plan to follow.
  - **One command, one undo step.** `apply_task_drag` re-derives the plan from the stored data (never trusts the screen's preview) and calls `tasks::update_many`: the dragged task and every pushed due date in one transaction, one activity row each. `AppState::run` already makes everything a command writes one undo step (spec 25), so no undo change is needed. The commands are `get_gantt`, `preview_task_drag`, `apply_task_drag`; the preview is the same function, called while dragging and answered by the backend, so what the screen shows is what is saved.
  - **The limit of a bar is a schedule fact.** `ScheduledTask` gains `earliest_start` and `held_by`: the first day the task could start whatever its own start date says, and the task that sets it. A drop earlier is refused with the reason (*can't start before X is done*); the screen clamps to the same day so the refusal is rarely met.
  - **A project's start date becomes a rule of the schedule.** *No open task starts before its project's `start_date`* (a past date changes nothing: nothing starts before today anyway). Until now the date was shown and never read. The room a project's bar shows at its left, and dragging it, mean something only if the schedule honours it, and the person asked for exactly that. It is applied in the forward pass of `schedule::compute_with`, so forecast, health, capacity, impact and the Gantt agree.
  - **Project and objective bars give room, they do not move tasks.** Dragging a flag writes `target_date` (`update_project` / `update_objective`, one undo step each): the backward pass gives every task more or less slack. The start mark writes `start_date`; the middle of a project's summary bar writes both. An ongoing objective has no target, so it has no flag to drag (ADR-0014). The start never passes the target and the target never passes the start.
  - **Sub-tasks and meetings.** Sub-tasks are drawn one step under their parent without being part of its bar (ADR-0017); meetings are not on the plan (ADR-0018), so they are not on the chart.
- **Consequences**: dragging is a normal edit: everything that reads dates and estimates follows, and *Weekly review* counts pushed due dates as slipped, which is true. A task whose bar was only where the schedule put it is **not** pinned by dragging its right edge, so a task with no start date still starts as early as it can; dragging its middle pins it. A moved bar can push due dates in other projects (the toast says how many). Because estimates change on resize, a task's *estimate* is no longer only something the person typed; the activity log records the change like any other. No migration, no new table, no demo-data change beyond a new snapshot (the Gantt of the seed), no export or sync change (they are ordinary dates and estimates).
- **Deviations**: `CLAUDE.md` §5.3 gains the project-start rule, §6 the three commands and §7 the screen in the sidebar list.
- **Related ADRs**: amends [ADR-0017](ADR-0017-subtasks-as-part-of.md) (the Gantt draws sub-tasks, still without effect on dates) and [ADR-0018](ADR-0018-meetings-as-a-built-in-task-type.md) (the Gantt is another place meetings are left out). Builds on [ADR-0012](ADR-0012-objective-colours.md) (objective colours on summary bars), [ADR-0014](ADR-0014-ongoing-objectives.md) (no flag on an ongoing objective) and [ADR-0021](ADR-0021-a-second-window-the-radar.md) (a project serving several objectives is drawn once, in the first).
- **Amended** (Gantt, easier to read, spec 58 phase 1): objective bars no longer wear the objective's colour; an objective's colour on the Gantt is only the dot by its name (as ADR-0012's dots elsewhere), and every bar is neutral or coloured by status or room, so colour means one thing on a bar. Project and objective bars are now as tall as a task's and filled for the share of tasks done, the room is a thin strip to the flag, and an ongoing objective's line fades out within a few weeks. Nothing about what a drag or drop writes changed.
- **Amended** (Gantt, accessible, spec 58 phase 2): every drag now has a keyboard and a click way that writes through the same commands with the same rules: the date box (click a bar or `Enter`: −1d / +1d and date fields; tasks via `apply_task_drag`, projects and objectives via `update_project` / `update_objective`) and `Alt+←/→` on project and objective rows (`Alt+Shift` for a project's start). A move the drag would stop at its limit is refused instead, with the same reason, and writes nothing. One undo step each, as before.
- **Amended** (Gantt, narrowed and found, spec 58 phase 3): the first view is no longer "projects folded": a project that needs a look (not finished, and late, out of room, or with blocked work; `core::gantt::needs_a_look`, carried on `GanttProject`) starts open. And a task can now be *started* from the chart, which spec 57 left out: dragging across an open project's add row opens quick-add with the project, start, due date and estimate filled in. Nothing is written until quick-add commits, through the usual `commit_quick_add`, so this ADR's rule that the Gantt writes only dates (and estimates) of existing work still holds for the chart itself. *By person* rows only read.
- **Amended by [ADR-0024](ADR-0024-order-of-work-is-a-schedule-rule.md)** (order of work, spec 60): a bar's earliest start can now also come from the step above it in its assignee's order (`held_by` names that task). Dragging still writes `start_date`, which wins when it is later; a drop earlier than the order allows is clamped and refused like one before a blocker.
