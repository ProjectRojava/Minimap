# ADR-0023: The backburner is a flag on the task, not a status

- **Context**: people want to set a task aside without cancelling it or losing where it stood: it may be blocked, in progress or not started. The board is organised by status, so a Backburner column is natural, but a task's status says where the work is, and setting it aside says nothing about that.
- **Decision**:
  - **A nullable date, `tasks.backburner_since`** (migration 0019), like `focus` (spec 37) and unlike a sixth `TaskStatus`. The task keeps its status, dates and links; bringing it back puts it back as it was. The board's Backburner column is derived from the flag (`Lane::Backburner`), so a card's column no longer comes from one field: dropping a card on a status column clears the flag and sets that status, dropping it on Backburner sets the flag.
  - **Why not a status**: `Done | Cancelled` is how "open" is written in `capacity`, `overview`, `this_week`, `people_frames`, `fog`, `weekly_review`, `impact`, `approach`, `orientation`, `export_md` and the UI, as `matches!` and not an exhaustive match, so a new variant compiles and silently gets each of them wrong in one direction or the other. A status would also overwrite `blocked` or `in_progress`.
  - **What it leaves and keeps**: it leaves the screens that say what needs doing now (This week, capacity and load, health counts, risks, *Your people*, the weekly review, the fog) through each module's own `is_open`/in-play rule gaining `&& !task.is_parked()`; it stays in the schedule, impact, the dependency graph, the Gantt and the export. **A task on the backburner that blocks other tasks keeps blocking them**: the schedule still counts it, so what waits on it keeps its place behind it (the alternative, dropping it from the schedule, would start the followers early and be wrong in the optimistic direction). The command returns how many open tasks wait on it and the message says so. A project that wants the task out of its plan cancels it or takes it off the project.
  - **Rules in the store**: finishing or cancelling clears the flag (not on undo or redo, which put things back as they were); a meeting refuses it. `set_task_backburner` refuses a finished or cancelled task and does nothing when the task is already in that state.
  - **`TaskFilter.hide_parked`** defaults to false so every caller that was not changed (pickers, search, links) still sees these tasks; only the Tasks list sets it.
- **Consequences**: the full export carries the field with the task; the demo data parks two tasks; the undo planner needs no new shape (`backburner_since` is in `store::undo::nullable_fields`); sync merges it with the row.
- **Deviation**: `CLAUDE.md` §4 lists `backburner_since` on Task and §6 the `set_task_backburner` command.
- **Related ADRs**: extends [ADR-0019](ADR-0019-fog-as-a-view.md) (a task on the backburner is never in play) and sits beside focus (spec 37). It is an ordinary field diff, so [ADR-0003](ADR-0003-activity-actions-and-patch.md) is unchanged.
- **Amended by [ADR-0024](ADR-0024-order-of-work-is-a-schedule-rule.md)** (order of work, spec 60): a task on the backburner still counts in the schedule, but not in a person's order of work: it neither waits for the step above it nor holds up the step below.
