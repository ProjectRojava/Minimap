# ADR-0010: Encryption by export-and-swap, keychain with a pending slot, no key fallback

- **Context**: spec 21 asks for optional SQLCipher encryption with a random key in the OS keychain or a passphrase, `PRAGMA rekey`, a backup first, and never logging the key. CLAUDE.md §8 describes `PRAGMA rekey`. The owner's answer to the open question: use the best option available, security is uncompromisable.
- **Decision**:
  1. **Export-and-swap instead of `PRAGMA rekey`.** Measured on the bundled SQLCipher 4.14: `PRAGMA rekey` cannot turn a plain database into an encrypted one (or back), and the backup API refuses to copy between plain and encrypted files (it does allow encrypted→encrypted with another key). Every change of key therefore uses `sqlcipher_export` into a new file keyed as wanted, verifies the copy (integrity check, `user_version`, every table's row count, schema objects; the export does not carry `user_version`, so it is set explicitly), then swaps it in with the original kept as `<db>.old` until the new file has opened, restoring it on any failure. The same machinery restores a plain backup into an encrypted database and the reverse.
  2. **Keys**: a random 32-byte key (OS `getrandom`) used raw (`x'hex'`), kept in the OS keychain through the `keyring` crate (pure-Rust Secret Service on Linux, so no system library is needed), or a passphrase typed at every start (SQLCipher's PBKDF2). One mode at a time; the keychain mode also yields a recovery key shown once. **No key is ever written to a file or the database**; with no keychain the passphrase is the only option.
  3. **Crash safety**: two keychain slots, `current` and `pending`. The new key is written to `pending` and read back before the database is touched, promoted to `current` after the swap; start-up tries both. A swap interrupted between the renames is undone at the next start; a leftover `.old` beside a working database is wiped.
  4. **Locked state**: an encrypted database with no usable key starts the app locked; the connection is `None` inside a `Vault` with its key and mode, and commands answer `locked` until `unlock_database` succeeds.
  5. **Hygiene**: key types wipe on drop (`zeroize`) and print as `<redacted>`; secrets from the UI are a `Secret` type with the same `Debug`; nothing logs them; the old plaintext file is overwritten with zeros before deletion (best effort); encrypted databases and backups are created owner-only on Unix; a wrong key waits ~0.75 s.
  6. **Backups**: created keyed with the live key (the destination is keyed before the pages are copied), so encrypted data never reaches a plain backup; a `pre-encryption` backup is taken before each key change and removed when it succeeds; backups made before encryption stay plain, are flagged, and can be deleted by the user in one step.
- **Consequences**: re-keying needs temporary disk space for a second copy and takes time proportional to the database; the encrypted file has no recovery if both the passphrase and the recovery key are lost (by design). Overwriting does not defeat flash wear levelling or journaling file systems; the first protection is encrypting early. The `keyring` Linux store needs a running Secret Service; without one the passphrase is offered.
- **Alternatives rejected**: an unencrypted key file or a key in the database as a fallback (violates "security is uncompromisable"); a home-made key-wrapping scheme to allow keychain *and* passphrase at once (new cryptography for little gain); relying on `PRAGMA rekey` (cannot do plain↔encrypted); a keychain-less "machine key" derived from hardware ids (guessable, not a secret).
