# ADR-0018: Meetings are a built-in task type with wall-clock times

- **Context**: a meeting happens at a time, starts and ends by itself, and is continued by later meetings (spec 38). Tasks have only a due *date*; task types (ADR-0016) are labels that change no behaviour; nothing in the app runs on a clock; and the backend has no reliable way to know the user's time zone (`store::today()` is UTC, the screen reads local time).
- **Decision**:
  - A meeting is a **task** whose type is the built-in id `meeting`. The settings list always holds it (`task_types::ensure_meeting` adds it when absent, brings it back when archived; it can be renamed and recoloured, not retired). So a meeting keeps the board, assignee, notes, links, undo, export and sync of a task.
  - **Time is wall-clock ("floating")**: the day is the existing `due_date`; two new nullable columns hold the start as a minute of the day (`start_minute`, 0-1439) and the length (`length_minutes`, none = the default hour). A weekly 10:30 therefore stays 10:30 across summer time and between devices, and a repeating meeting only needs the next date.
  - **The clock is the screen's.** `advance_meetings(clock)` takes the local date, minute and UTC offset the screen reads from the browser, every half minute and when it opens; the pure rule is `core::meeting::next_status` (to do -> in progress at the start, to do or in progress -> done at the end; a meeting missed while the app was closed goes straight to done, with `completed_at` at the end instant computed from the offset). The command uses `run_vault`, which does not record an undo step, so the clock never becomes "the last change". A clock more than two days from the real date is refused.
  - **Follow-ups** are a new edge `follows_up` (meeting -> meeting, follow-up -> original): one original each, any number of follow-ups, no loops (`core::meeting::check_follow_up`, `store::meetings::check_follow_up`, called from `check_new_edge`). A repeating meeting's next one is linked to the one that ended in the same transaction.
  - **Meetings are not planned work**: `store::tasks::list_planned` (every task but meetings) feeds the schedule, impact, overview/health, capacity and the dependency graph; This week gives them their own list and keeps them out of every red flag; the weekly review leaves them out.
- **Why not a separate node type**: it would need its own table, activity, undo, merge, export, tombstones, search, demo removal and every task screen again for what is a task with a time.
- **Why not instants**: an instant needs a stored zone to repeat "10:30 every Monday" correctly across a summer-time change, and a zone is exactly what the backend doesn't have.
- **Consequences**: meetings move on only while the app is open (a meeting that ended while it was closed is closed on the next start, which is the same result). Two devices open at once both apply the same rule and converge. If the user travels, 10:30 stays "10:30 on the clock where they are". A meeting's due date and time can't be cleared; changing the type away drops the time. A new column pair and an edge type: demo data, export (automatic: the structs are the files), undo (`nullable_fields`) and the sync merge (by column) all cover them.
- **Deviation**: `CLAUDE.md` §4 gains the task's `start_minute` / `length_minutes`, the `follows_up` edge and its invariant.
