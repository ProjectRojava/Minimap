# ADR-0021: A second window: the radar

- **Context**: the product is named after the game minimap: a small map you glance at without leaving what you are doing. A screen inside the main window cannot be that, because it is not there while you are in a call or another app. We want **a small, frameless window, optionally on top of other apps, that shows your world centred on you** and from which you can jump to an item (`docs/product-design/10-radar-window.md`, spec 53). Until now the app had one window and used no events.
- **Decision**:
  - **One new window, label `radar`, created by Rust, not by the webview.** `commands::radar::open_radar_window` builds it with `WebviewWindowBuilder` (no decorations, resizable, 260 by 260 logical pixels to start, at least 200 by 200, no task-bar entry, opaque, the theme's background colour until the page paints). The webview therefore needs no `window:create` permission. It loads `index.html`, the same bundle as the main window (so the page resolves in the dev server and in a built app without any routing rule), and `App` renders `RadarApp` (no shell: no sidebar, title bar, status bar, toasts or pane) when `window.__TAURI__.window.getCurrentWindow().label` is `radar`, falling back to the path `/radar` (a plain browser). Opening an open radar brings it forward. Closing the **main** window closes the radar (`on_window_event`), so the app exits normally.
  - **A capability of its own, narrower than the main one.** `capabilities/radar.json` is for the window `radar` only and lists `allow-get-radar`, `allow-get-data-revision`, `allow-open-in-main`, `allow-close-radar`, `allow-set-radar-on-top`, `allow-get-settings` (the theme), `core:window:allow-start-dragging` (move it by its top bar and empty space) and `core:window:allow-start-resize-dragging` (an undecorated window has no resize border of its own on Linux and macOS; Windows has one natively). **It can call no command that writes anything**, apart from the two that touch only the window and a device-local setting (`set_radar_on_top`). A test parses the file and asserts the list. The main window's `default.json` gains `allow-open-radar`, `allow-close-radar`, `allow-toggle-radar` and `allow-set-radar-on-top` (a spec addition: the shortcut and the title-bar button toggle without the page having to know whether the radar is open).
  - **Events, for the first time, in one direction.** The radar asks the main window to open an item with `open_in_main(node)`: Rust unminimises, shows and focuses `main`, then `emit_to("main", "minimap://open", node)`. The main window listens (`window.__TAURI__.event.listen`), which needs **`core:event:allow-listen` in `default.json` only**; a test asserts the radar capability has no `core:event` permission. The listener selects the item and navigates to its list screen. Nothing else is sent by event: refreshing is still **polling**, like ADR-0011.
  - **Layout in core, drawing in the UI.** `minimap_core::radar::build` is pure: it takes the schedule-free inputs the other screens already compute (tasks, projects, objectives, `contributes_to` links, the Overview for project health and safe zone, the fog report, the pings, the approaching report, My view's scope, the rings) and returns sectors, blips, edge marks and a footer in abstract polar units (radius 0 to 1, angle clockwise from 12 o'clock). Angles come from a hash of the item id (`sync::fnv1a`), never from chance, so nothing jumps between refreshes and the result does not depend on the order of the inputs (a proptest). `ui/src/radar_geom.rs` is the only place that knows pixels. The radius is piecewise-linear in **working days** until the due date or target, so the rings mean what the schedule means.
  - **`get_radar` reuses, never repeats.** `commands::radar::radar_at` calls `my_scope_at`, `overview_at`, `fog_at`, `list_pings_at` and `approaching_at`; no query of its own. It uses `store::today()` like every other screen (the spec's `utc_offset_minutes` argument was left out: the rest of the app counts "today" in UTC, and a radar with another idea of today would disagree with This week).
  - **Refresh** is two commands: `get_data_revision` (the newest activity row plus how many times the sync engine has merged another computer's data; cheap) every five seconds, and `get_radar` when it moved or once a minute. The number is read before the picture is built, so a change that lands during the build shows up as a newer number. A settings change writes no activity, so it appears at the next minute.
  - **Device-local, never synced.** Where the window sits (`local.radar_geometry`, physical pixels, in `app_meta` like the other `local.*` keys, kept by a small thread that writes once the window has been still for 600 ms and at once when a window closes) and three settings (`radar_on_top`, `radar_open_at_start`, `radar_rings`, added to `settings::LOCAL_ONLY` like the theme). A remembered place is brought back onto a screen that exists now (the one it overlaps most), else the bottom-right corner of the primary screen. Whether the radar stays on top lives in the setting alone, not also in the geometry.
  - **The view is shared through `localStorage`.** The two windows are one origin, so the remembered view (`minimap.view`, ADR from spec 50) is shared; each listens for the `storage` event and follows the other. No backend involved. My view without a "me" is the Portfolio view, as everywhere.
  - **Sectors are the in-scope objectives that are not done**, ordered by priority then title, with an "Other" sector for items that serve none (or only an objective outside the view). An item that serves several appears once, in the first of them. An objective's colour is its rank among all objectives by id, exactly as ADR-0012 derives it, so a sector's rim matches its chips elsewhere.
- **Consequences**: a new `Radar`/`Sector`/`Blip`/`EdgeMark`/`Footer` family in `minimap-types`; three more `Settings` fields; one more core module and one more command module; `tauri::Builder` gains `on_window_event` and a managed `RadarSaver`. The Help wiki has a page, *The radar*. Nothing is stored in the database except the three settings and the geometry (all device-local), so there is no migration, no demo-data change, no export change and no undo change. Window behaviour (on top, no focus stealing, resizing, drag) can only be checked by running the app on each OS.
- **Deviations**: `CLAUDE.md` §6 gains the radar commands (`get_radar`, `get_data_revision`, `open_radar`, `close_radar`, `toggle_radar`, `set_radar_on_top`, `open_in_main`) and its capabilities line now names a second capability file. `BlipKind::Objective` from the design doc's sketch was left out: no rule makes an objective a blip (the objectives are the sectors).
