# ADR-0024: The order of work is a rule of the schedule, stored as a step on the task

- **Context**: the schedule (CLAUDE.md 5.3) is critical-path only: a task starts as soon as its `blocks` predecessors, its own start date, its project's start and today allow, and nobody's time is counted. One person's tasks therefore all start on the same day, and the Gantt draws them side by side. Spec 60 lets the user say, per person, what is done first (steps top to bottom) and what is done together (side by side).
- **Decision**:
  - **The order constrains the schedule; it does not write dates.** `core::order::links` turns each person's steps into "comes after" pairs (every task of the nearest earlier step → every task of the step), and `schedule::compute_with` adds them to the `blocks` graph with lag 0. The forward pass then gives each task its start; the backward pass, slack and the critical path see the same pairs, so the forecast, health, impact, capacity, the dependency graph's facts and the Gantt all agree. `start_date` keeps its meaning (the person's word, "not before") and is never written by the order, so an early finish moves everything below it up, and a slip pushes it down.
  - **Stored as `tasks.order_step`** (migration 0020, nullable integer), the task's step in its assignee's order. Not on the `assigned_to` link: a link's attributes can't be undone (`core::undo` refuses " link" diffs, there is no edge id in the diff), while a task field is an ordinary patch (undo, sync merge, export and the activity log need nothing new). A task with two assignees has one step, read in each person's order; a reorder renumbers only the person's own tasks, so the shared task's number can shift the other person's order. This is rare and visible on the screen.
  - **What the order ignores**: tasks that are done, cancelled, archived, meetings, parked (spec 59) or unassigned; and pairs whose second task is already in progress (it has started; its date is a fact). Clearing: changing the assignee, finishing or cancelling clears `order_step` (not on undo or redo).
  - **Conflicts never break the schedule.** `set_order` refuses an order that contradicts `blocks` (store, via `core::order::check`, with the task names). A pair that would close a loop with links already in the graph is skipped in `compute_with` (pairs are added after every `blocks` link, each only if it makes no loop), so a later `blocks` link wins; `core::order::view` lists the dropped pairs as conflicts.
- **Consequences**: projects can go amber or red as soon as someone has an order: the forecast now counts that person's time, which is the point. `get_schedule` reads `assigned_to` links as well as `blocks`. Capacity still reads the schedule, so an ordered person's load spreads over the weeks instead of piling up in the first one. The demo data gives one person an order. Not built: tracks, levelling, writing dates.
- **Deviation**: `CLAUDE.md` §5.3 gains "a person's order of work (spec 60)" as an input of the forward pass; §4 lists `order_step` on Task; §6 the `get_order` / `set_order` commands; §7 the *Order* screen.
- **Related ADRs**: extends [ADR-0022](ADR-0022-the-gantt-writes-dates.md) (the Gantt's bars follow the order; dragging a bar still writes `start_date`, which still wins when later). The order ignores parked tasks, unlike the rest of the schedule ([ADR-0023](ADR-0023-the-backburner-is-a-flag.md)). Meetings stay out of the plan ([ADR-0018](ADR-0018-meetings-as-a-built-in-task-type.md)).
- **Amended** (the order writes start dates, spec 60 follow-up): the decision that the order "does not write dates" and "`start_date` is never written by the order" no longer holds. After every command that writes, `AppState::run` calls `store::order::sync_dates`, which runs `core::order::start_dates`: the schedule (as before, with the order as a rule) is computed and each task that comes after another in someone's order (so not step 1, not in progress, not outside an order) gets `start_date` = the day the schedule starts it, **when that is later than the date it has** (or it has none). The rule is a ratchet on purpose: a date is never moved earlier, so a start date the person typed or dragged to (ADR-0022) that is later than the order's still wins, and an early finish above no longer pulls the dates below up (the person asked for real, visible dates; ADR-0022 declined to pin start dates for the same reason that they then stop following). A slip above moves every date below down. The writes are ordinary task updates (activity rows, `updated_at`, sync, export), made before the command's undo step is recorded, so one Undo takes the change and the dates back; undo and redo themselves do not re-run it. `set_order` also runs it so its answer has the dates. A schedule that cannot be made writes nothing. Demo data needs nothing: the dates appear on the first write.
- **Amended** (the order fills in empty due dates, spec 60 follow-up): the same step (`core::order::dates`, replacing `start_dates`) also gives every open ordered task that has an estimate and no `due_date` a due date: the last working day the schedule gives it (start plus estimate). Only empty due dates are written; a due date that is set is a promise (ADR-0022) and is never moved, so a slip shows as *finishes after its due date* instead of silently pushing deadlines.
- **Amended** (the queue and My team, spec 61): the Order screen can now change who a task is assigned to. On *My team* (everyone in Minimap side by side, you first), dragging a task to another person's column runs `give_task`: `store::order::give` makes that person the task's only assignee (`tasks::set_assignee_in_tx`, which still clears the old step) and sets their order in the same transaction, so a refused order leaves the assignee as it was and one Undo takes both back. Each person still has their own order; nothing here is an order across people. `WorkOrder` also carries `ruler` (`core::order::ruler`, 15 working days) and `today` for the bars; they change no rule of the schedule.
- **Amended** (the ruler grows, spec 61 follow-up): the ruler is no longer always 15 working days. `core::order::ruler` keeps 15 as the least and grows (up to `RULER_MAX` = 130) until the last card's finish is on it; the Order screen scrolls sideways when it is longer than the window. It still changes no rule of the schedule.
